# 许可证判断边界与权威来源

在许可证层审查时读取。这里是核验导航，不能替代实际取得版本的许可证、例外及有效授权。每次形成具体法律结论时在线复核原文并记录访问日期；当前网页不能证明历史文件采用何种许可。无法读取原站时可使用 SPDX 对应版本文本，并说明来源。

## 版本与授权

辨明 GPL/LGPL/AGPL 的具体版本及 only/or-later；MPL 1.1/2.0、EPL 1.0/2.0、Apache 1.x/2.0、BSD 各变体不能互换。双许可要核实谁授予何种选择权；组合中的每个组件都需授权，根目录的宽松许可不能覆盖另行许可的依赖。

`AND` 表示须同时满足，`OR` 表示在有效选择权内择一，`WITH` 表示相关例外。以实际声明为准，不能仅靠项目名称、仓库标签或 SPDX 识别结果完成法律分析。兼容性还取决于组合方向及受覆盖作品范围。

## 链接、进程与网络边界

按实际技术关系记录复制代码、修改、静态／动态链接、加载插件、共享结构、IPC/RPC 以及功能／部署依赖。进程、容器、插件、HTTP API 都是技术事实，不是统一适用于所有许可和法域的法律安全港。

区分受覆盖组件自身的义务与对组合／自研部分的影响。独立服务可能降低耦合，但服务若含受覆盖代码仍需分析其许可；隔离不能抹去复制事实。SaaS 服务端、用户下载的前端 bundle 和交付客户的容器分别核验。

AGPL 3.0 第 13 节核验应记录实际请求／响应路径：外部用户是否经网关或业务后端与修改版服务交互，以及源码获取入口面向哪些用户。将这种交互与仅消费独立内部批处理结果的情形分别分析；“没有直连”不能单独排除网络条款，存在中间层也不能直接证明所有调用方属于同一作品。

## 同源性、衍生作品与权利人主张

代码相同可证明表达一致，但不单独证明未经授权或未履约。相似度低不能排除复制了少量重要表达；相似度高可能源于共同依赖、生成器或标准实现。检查权利归属、可保护性、取得路径、授权及履约事实后，再评估法律风险。

对基金会 FAQ、项目方解释、律师意见和司法裁判分别标注来源类型，不把任一项目方声明写成所有法域通用的法律结论。需要引用案例时核验法院、案号、裁判日期、事实适用性与裁判状态；找不到原始材料就明确标为未核验。

商业许可只覆盖授权人有权许可及合同明确涵盖的内容。核查贡献者、第三方依赖及资产权利；不能默认一家厂商可豁免全部开源义务。替换、重写、补声明、取得后续授权与历史责任分别分析。
